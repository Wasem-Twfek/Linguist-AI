4.1 Challenge: Role-Based Access Control with Redirect Loop Prevention
-----------------------------------------------------------------------

Problem: 
When middleware redirects users to their correct dashboard, it can create infinite redirect loops if not handled carefully. For example, a student accessing /teacher/dashboard should redirect to /student/dashboard, but the redirect logic must not trigger again.

Solution Implemented (middleware.ts lines 232-264):

if (userRole !== requiredRole) {
  const correctDashboard = getDashboardForRole(userRole)
  
  // CRITICAL: Prevent redirect loops
  if (pathname !== correctDashboard) {
    return NextResponse.redirect(new URL(correctDashboard, request.url))
  }
  
  // Already on correct dashboard, allow through (prevents loop)
}

Technical Details:
- Middleware checks if the current pathname equals the target dashboard
- If user is already on their correct dashboard, request is allowed to proceed
- This prevents the middleware from continuously redirecting /student/dashboard → /student/dashboard

4.2 Challenge: Handling Base64 Audio for Gemini API
----------------------------------------------------

Problem:
MediaRecorder produces WebM blobs, but Gemini API requires audio in a specific format with base64 encoding. Direct blob transmission is not supported.

Solution Implemented (actions.ts lines 182-202):

// Read audio file as ArrayBuffer
const arrayBuffer = await audioFile.arrayBuffer()
const buffer = Buffer.from(arrayBuffer)

// Convert to base64 for Gemini API
const base64Audio = buffer.toString('base64')

// Create Gemini content part with inline data
const contentParts = [
  {
    inlineData: {
      data: base64Audio,
      mimeType: 'audio/webm'
    }
  },
  { text: promptText }
]

Technical Details:
- Audio file converted to ArrayBuffer → Buffer → base64 string
- MIME type explicitly set to audio/webm for Gemini compatibility
- Content parts array combines audio data with text prompt
- Model configured with responseMimeType: 'application/json' for structured output

4.3 Challenge: Session-Result Data Integrity with Attempt Numbering
--------------------------------------------------------------------

Problem:
Students can start recordings but abandon them before submission. If sessions are created before validation, the database accumulates orphaned records, and attempt numbers become inaccurate.

Solution Implemented (actions.ts lines 302-349):

// Get attempt number (count existing COMPLETED sessions only)
const { data: existingSessions } = await supabase
  .from('sessions')
  .select('id')
  .eq('user_id', user.id)
  .eq('assignment_id', assignmentId)

// Count only sessions that have results (valid completed attempts)
const { data: existingResults } = await supabase
  .from('results')
  .select('session_id')
  .in('session_id', existingSessions.map(s => s.id))

// Attempt number = count of valid completed attempts + 1
const attemptNumber = (existingResults?.length || 0) + 1

// Create session record - ONLY after all validations pass

Technical Details:
- Validation-first approach: Audio duration, file size, and transcript length validated BEFORE session creation
- Attempt numbering logic: Only counts sessions with associated results (valid completions)
- Cleanup on failure: If session creation fails after audio upload, uploaded file is deleted:
  await supabase.storage.from('assignment-audio').remove([filePath])


5. UNSOLVED PROBLEMS & CHALLENGES
================================================================================

5.1 Safari Browser Audio Compatibility
---------------------------------------

Problem:
MediaRecorder API has inconsistent support across browsers. Safari (especially on iOS) may:
- Record in audio/mp4 format instead of audio/webm
- Fail to start recording due to WebRTC implementation differences
- Require user gesture triggers that don't align with React event handlers

Technical Reason:
- Safari uses Apple's proprietary CoreMedia framework for media recording
- WebM container is not natively supported; Safari prefers MP4/CAF formats
- The current code hardcodes MIME type as audio/webm (audio-recorder.tsx line 59):
  const blob = new Blob(chunksRef.current, { type: 'audio/webm' })

Why Difficult to Solve:
- Requires browser detection and conditional MIME type selection
- Gemini API may not support audio/mp4 format equally well
- Would need testing infrastructure with real Safari devices (not just emulators)
- Workaround: Currently undefined; platform may fail silently on Safari

5.2 Gemini API Latency and Rate Limiting
-----------------------------------------

Problem:
Gemini API calls take 5-15 seconds for audio evaluation, creating poor UX. Additionally:
- Free tier has quota limits (requests per minute/day)
- No fallback evaluation method if API is unavailable
- Synchronous blocking: User must wait for response before seeing results

Technical Reason:
- Audio processing is computationally expensive (transcription + analysis + scoring)
- Current implementation uses synchronous await model.generateContent(prompt) with 20-second timeout
- No queue system or background job processing
- No caching of similar audio patterns

Why Difficult to Solve:
- Real-time evaluation is a core feature requirement (immediate feedback)
- Adding queue system (e.g., Bull, Redis) requires infrastructure beyond Supabase free tier
- Alternative models (Whisper, Azure Speech) require separate API keys and integration work
- Current mitigation: Timeout handling and error type classification, but no fallback scoring

5.4 No Rate Limiting on Submissions
-------------------------------------

Problem:
Students can submit unlimited assignments, potentially:
- Exhausting Gemini API quota (costs money or blocks service)
- Flooding database with invalid attempts
- Creating unfair advantage through repeated submissions

Technical Reason:
- No rate_limit_log table implemented (suggested in SENIOR_REVIEW.md)
- Server action submitAttempt has no throttling logic
- Client-side validation (3-second minimum) is easily bypassed

Why Difficult to Solve:
- Requires new database table + RLS policies
- Must track per-user submission timestamps
- Balancing usability (allow retakes) vs. abuse prevention
- Recommended approach: 
  CREATE TABLE rate_limit_log (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES auth.users(id),
    action TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT now()
  );
  Check last 5 minutes for same user+action before allowing submission

5.5 Audio Storage Costs and Lifecycle Management
--------------------------------------------------

Problem:
All audio files are permanently stored in Supabase Storage with:
- No automatic cleanup policy
- No retention period enforcement
- Growing storage costs over time

Technical Reason:
- Supabase Storage doesn't have built-in lifecycle policies (like AWS S3)
- No cron job implemented to delete old files
- Database results table has no expires_at column

Why Difficult to Solve:
- Requires external scheduler (Vercel cron, GitHub Actions, or Supabase Edge Functions)
- Must balance data retention (for analytics) vs. storage costs
- GDPR compliance requires clear data deletion policies
- Recommended approach: 
  - Add expires_at column to results (default: now() + 90 days)
  - Create cleanup script that deletes audio files for expired results
  - Run via Vercel cron job or manual execution
